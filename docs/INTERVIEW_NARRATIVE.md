# 星旅 Agent · 产品思考与面试叙事

## 一句话介绍

星旅 Agent 是一个把“AI 多智能体规划 + 真实数据接入 + 人工审核 + 社区分享”串起来的旅行平台。

## 核心问题

旅行规划看似简单，实际难在三个地方：

1. 信息要真实：景点、店名、价格不能靠模型编。
2. 行程要合理：不能一天排 20 个景点。
3. 用户要能改：生成后还能按需求调整，而不是重新生成。

## 我的技术取舍

### 1. 为什么拆多智能体？

不是因为“多智能体”听起来高级，而是因为任务边界清楚：

- 景点检索需要搜索 + 高德 POI
- 美食推荐需要搜索 + 高德店名
- 交通规划需要高德路线
- 路线优化和校验是独立环节

拆开以后可以并行执行、独立失败、单独统计，主 Agent 只负责理解和调度。

### 2. 为什么先保留 SQLite？

个人阶段 SQLite 部署成本低、迁移简单、数据都在本地，适合做产品验证。

生产上线前再迁 PostgreSQL，不是“不会用”，而是“知道什么阶段用什么”。

### 3. 为什么不爬美团/大众点评实时人均？

个人开发者没有企业资质，硬爬会违规，而且数据随时失效。

所以我的方案是：

```text
高德参考价 + 管理员价格库 + 用户实际价格反馈 + 人工审核
```

这叫“数据可信度分级”，比假装实时更诚实，也更可持续。

### 4. 为什么攻略要人工审核？

AI 生成内容质量不稳定，真实内容是这个平台的核心资产。

所以攻略发布必须过管理员审核，行程则属于用户个人直接使用。

### 5. 搜索为什么做多 Provider 降级？

免费 Key 会失效、额度会用完。

我做了 Tavily → SerpAPI → Bing → Google → Serper → Brave → 多平台爬取 → 内置语料，再加 24h 缓存，保证不会因为一个 Key 挂了整条链路失败。

### 6. 为什么局部调整不做全量重生成？

用户改一个日期，不需要重新搜所有景点。

主 Agent 输出 changed_fields，只派相关子 Agent，旧行程内容保留，成本更低，体验更稳。

## 我踩过并修掉的坑

- 搜索 Provider 失败没有降级 → 加 failover + 缓存
- 反思结果没有真正回流 → 改成有次数上限的反思重试
- 只改日期会把旧行程清空 → 保留旧行程内容
- 预算重算后被覆盖 → 每次重算后强制执行预算
- 并发保存会话撞主键 → INSERT OR IGNORE
- 攻略标题混进店名 → 规则过滤 + 大模型提取店名
- 交通全部 20 分钟 → 补齐高德真实路线
- 管理员登录白屏 → 权限接口兼容 admin

## 上线路径

```text
1. GitHub 仓库 + 在线 Demo
2. 50-100 名种子用户
3. PostgreSQL 迁移
4. 邮箱验证 + 内容审核 + 隐私协议
5. 付费搜索/LLM + 用户配额
6. 交易闭环
```

## 3 分钟面试叙事

1. 我做一个 AI 旅行规划平台，核心不是生成文字，而是生成“真实、合理、可调整”的行程。
2. 我用 1 个主 Agent + 5 个子 Agent 拆任务，并行执行，单独失败。
3. 数据用高德、和风天气、搜索、攻略抓取，并做可信度分级。
4. 用户改日期不会全量重生成，预算不会超。
5. 我还做了评测、冒烟测试、Docker、CI、运行 trace。
6. 我清楚个人阶段拿不到美团/景区官方 API，所以用价格库 + 用户反馈 + 人工审核替代。
7. 下一步是部署上线、PostgreSQL、真实用户和交易闭环。
