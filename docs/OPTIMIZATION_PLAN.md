# 星旅 Agent 下一阶段优化计划书

> 版本：v2.0
> 日期：2026-08-21
> 目标：把当前“功能完整的 Demo 级产品”升级为“可小范围上线、可持续运营、可融资/面试深挖的 Agent 业务系统”

## 1. 现状定位

项目已经具备完整的业务闭环：多智能体行程生成、多轮调整、真实搜索/地图/天气、RAG 检索、版本化、人工审核、攻略社区、RBAC、指标与离线评测。

当前更接近“单实例可演示的产品”，距离“企业级可上线系统”主要差在：

- 链路稳定性：搜索 provider 失败没有自动降级，SerpAPI 额度用完会导致整次生成失败。
- 反思流程：`_quality_router` 目前固定返回 `finish`，反思结果没有真正回流重试。
- 局部调整：日期、交通等单一调整也会触发景点+美食全量重跑，成本高且容易改坏旧行程。
- 真实数据：票务、餐厅、打车、单车仍是占位配置，只有搜索/地图/天气是真实数据。
- 评测体系：24 条用例偏规则校验，没有覆盖真实搜索、价格一致性、来源真实性、多 Agent 协作。
- 工程化：SQLite + 进程内指标 + 每次请求新建 Agent，适合演示但不适合多人并发。

## 2. 优化总目标

1. 链路稳定：搜索、地图、天气任一数据源失败时自动降级，生成不中断。
2. 成本可控：一次完整行程生成的 token/API 调用成本下降 30%-50%。
3. 结果可信：景点、美食、交通、价格全部带真实来源，价格与人数、日期、城市一致。
4. 体验完整：用户能直接编辑行程、看地图、导出、分享，而不是只能靠对话改。
5. 可运营：社区审核、投诉、封禁、内容安全、数据报表达到运营要求。
6. 可证明：新增 50+ 条端到端评测，覆盖意图、拆解、子 Agent、反思、成本、来源真实性。

## 3. 优化主线 A：Agent 流程链路

### A1 搜索与工具可靠化

当前问题：
- `WebSearchTool.search()` 按 provider 顺序选择，SerpAPI/Tavily 抛错不会继续尝试下一个。
- 同一城市同一天的搜索会被反复执行，浪费额度与延迟。

改造：
- 改为“按优先级逐个尝试，全部失败再走内置语料”的 failover 链。
- 搜索失败时记录 `provider=fallback`，并进入可观测指标。
- 增加两级缓存：SQLite 持久缓存 + 进程内 LRU，key 为 `city|category|query|date`，TTL 默认 24h。
- 把多平台搜索、内容抓取放到后台任务，前端先生成骨架，再逐步填充。

验收：
- 任意一个搜索 Key 失效，仍能完成行程生成。
- 重复生成同一城市不重复调用外部搜索。

### A2 意图识别与局部调整

当前问题：
- `_build_adjust_subtasks()` 对“改日期/改交通”也会强制补上景点和美食子任务。
- 调整后的行程可能变成“全量重生成”，旧行程里用户认可的景点会被冲掉。

改造：
- Main Agent 输出 `changed_fields`：date / city / days / travelers / budget / transport / attraction / food / route。
- 根据 `changed_fields` 生成最小子任务集：
  - 只改日期：只更新参数 + 重查天气 + RouteAgent 校验。
  - 只改交通：只派 TransportAgent + RouteAgent。
  - 去景点：只派 AttractionAgent 替换 + RouteAgent 重排。
  - 改预算：只派 FoodAgent/AttractionAgent 重算金额 + Validator。
- 增加 `diff_plan`：比较新旧行程，输出哪些 Day/Item 被增删改，前端用高亮展示。
- 旧行程未被触发的部分直接保留，避免“改一处全变”。

验收：
- “只改出发日期”时，不调用景点/美食外部搜索。
- 调整后旧行程里未涉及的内容保持稳定。

### A3 反思与自动重试

当前问题：
- 图里已经有 `ReflectionAgent` 和 `synthesis -> reflect`，但 `_quality_router` 固定 `finish`，反馈没有回流。

改造：
- `_quality_router` 改为真正的条件路由：
  - `quality_ok=true` -> finish
  - `quality_ok=false` 且 `retry_count < max_retries` -> synthesis
  - 重试次数达到上限 -> finish，但把问题写进 `quality_issues`
- 每次重试传入上一版行程 + 反思反馈，SynthesisAgent 只修正问题项，不整版重写。
- 反思失败原因分类：价格不合理、时间冲突、重复景点、缺真实来源、交通不可达。
- 每次反思重试都写入 `agent_results` 与评测报告。

验收：
- 明显不合理行程（比如一天超过 22 点、同一美食重复）能在 2 次重试内修正。
- 重试次数、原因、耗时全部可追踪。

### A4 流式生成与后台任务

当前问题：
- 每次请求都新建 `TravelLLM / HybridSearcher / create_agent`，没有复用。
- 流式只是阶段事件 + 最终 token 补发，不是真正的逐 token LLM 流。

改造：
- LLM、Searcher、Agent 改为应用级单例/池化，避免重复初始化。
- 对话接口接入 DeepSeek/OpenAI 原生流式，实时输出 main_parse、子 Agent 状态和最终内容。
- 把天气刷新、攻略抓取、价格校验放入后台任务队列，不阻塞主链路。
- 前端断线后保留 `session_id + run_id`，可查询进行中的任务并恢复页面。

验收：
- 首条阶段事件 < 5s，完整行程 < 90s。
- 切走页面后任务继续，回来可看到历史对话与结果。

### A5 上下文与版本

- 每个 `run_id` 保存完整 trace：输入改写、TaskPlan、子 Agent 结果、工具调用、token、耗时。
- 对话上下文按 token 预算裁剪，只保留与本次调整相关的历史。
- 行程版本增加“对比视图”：v1 vs v2 的差异，而不是只能看最新版。
- 引入 `itinerary_versions.diff` 字段，前端直接渲染增删改。

## 4. 优化主线 B：真实数据与业务闭环

### B1 数据源接入矩阵

| 数据 | 现状 | 下一阶段 |
|---|---|---|
| 景点 POI/地址/简介 | 高德 POI + 搜索 | 高德 POI 全量、营业时间、评分、官方预约链接 |
| 美食 | 搜索 + 内置语料 | 高德 POI 找真实店名/地址/人均，或接入美团/大众点评开放数据 |
| 交通 | 高德路线估算 | 高德驾车/公交/骑行 API 真实距离时间，出租车费用估算 |
| 天气 | 和风天气 | 出发日期自动刷新 + 行程当天预警推送 |
| 酒店 | Booking RapidAPI（已暂停） | 按入住晚数返回房价、房型，可选接入 |
| 门票 | 占位 API | 官方票务/景区开放接口，至少接入可预约景区 |
| 打车/共享单车 | 占位 API | 高德出行/滴滴开放平台或明确标注估算价 |

### B2 内容可信度

- 搜索结果进入 RAG 前增加字段：`freshness`、`domain_trust`、`is_official`。
- 价格字段统一为 `amount / currency / unit / source / updated_at`。
- 生成行程必须带 `sources`，前端每个景点/美食/交通可点击跳转来源。
- 对抓取的攻略页面做去重、清洗、正文抽取，不要直接把标题当店名。
- 高风险内容（价格、营业时间、限流预约）默认标注“需以官方实时信息为准”。

### B3 城市覆盖

- 当前城市中心表只有约 20 个城市。
- 改为“城市中心 + 高德地理编码”动态获取坐标，所有国内城市可用。
- 内置语料优先覆盖热门 50 城，其余城市走真实搜索 + 高德 POI。
- 新增“城市知识库”后台管理，管理员可补充景区、美食、交通说明。

## 5. 优化主线 C：产品功能

### C1 行程编辑体验

- 左侧保留 AI 对话，右侧行程改成可直接编辑的“时间轴编辑器”：
  - 拖拽调整景点顺序
  - 单日增删景点/美食/交通
  - 修改出发时间、停留时长、预算
  - 修改后自动触发局部子 Agent 校验
- 增加“重试该天”“换掉该景点”“重新生成这一日”按钮。

### C2 地图与协作

- 行程右侧增加高德地图视图：POI 打点、每日路线连线、酒店/餐饮/景点分层。
- 支持多人协作规划：邀请链接、共同编辑、留言评论、权限（查看/编辑）。
- 支持多城市串联：A 城市 3 天 + B 城市 2 天，主 Agent 按城市拆分规划。

### C3 攻略社区

- 增加帖子举报、拉黑、敏感词过滤、图片安全审核。
- 攻略广场增加城市、标签、热度、发布时间筛选。
- 支持一键“把这篇攻略的推荐加入我的行程”。
- 增加作者主页的数据：攻略数、被赞数、被收藏数、粉丝。

### C4 导出与分享

- PDF/图片导出整份行程，不是只导出当前 Day。
- 一键复制 Markdown/文本到小红书、朋友圈。
- 分享链接支持只读模式，无需注册即可查看。

### C5 移动端

- 先做 PWA：离线缓存、添加到桌面、推送天气/预约提醒。
- 再做微信小程序/H5，作为核心获客渠道。

## 6. 优化主线 D：工程与运营

### D1 架构

- 建议演进：FastAPI + LangGraph + SQLite -> PostgreSQL + Redis + 对象存储。
- SQLite 保留单机演示，新增 `data_source=sqlite/postgres` 配置。
- 上传文件从本地目录迁移到对象存储，或至少做目录隔离与防盗链。
- 新增任务队列（Redis + 简单 worker），处理抓取、天气刷新、价格校验、PDF 生成。

### D2 可观测性

- 进程内 metrics 保留，同时增加持久化 trace 表。
- 接入 OpenTelemetry 或自建 trace 接口，记录每个 `run_id` 的节点耗时与工具调用。
- 增加成本报表：按用户、按意图、按子 Agent 统计 token 与金额。
- 增加告警：外部 API 失败率、生成失败率、平均耗时、审核积压。

### D3 评测升级

- 现有 24 条规则用例保留，新增：
  - 真实搜索用例：随机城市必须返回真实景点/美食且带来源。
  - 价格一致性用例：人数、晚数、车费计算与总消费一致。
  - 局部调整用例：只改日期时不得重跑景点搜索。
  - 反思重试用例：明显冲突行程能被修正。
  - 多 Agent 并行用例：三个子 Agent 是否并行执行、结果是否合并。
  - 来源真实性用例：生成结果里的店名/地址必须来自搜索来源。
- 增加人工评估池：20 个真实城市需求，由管理员对“可用性、真实性、合理性”打分。
- 增加回归门禁：`pytest tests -q` + `python -m app.eval.runner` 作为 CI 必过项。

### D4 安全与合规

- 注册增加邮箱/手机验证，密码强度与登录失败锁定。
- 增加 refresh token，减少长期固定 token 风险。
- 对用户生成内容做图片鉴黄鉴政、文本敏感词、诈骗链接检测。
- 外部搜索抓取遵守 robots、频率限制，公开数据只做摘要与溯源，不搬运全文。
- 数据最小化：日志脱敏、删除账号时清理个人数据。

## 7. 优化主线 E：商业化

- 免费额度：每天 N 次基础行程，超出后按 token 计费或开会员。
- 会员等级：基础版（单城）、专业版（多城 + 地图 + PDF）、家庭版（多人协作）。
- 交易闭环：酒店预订、景区门票、打车券通过联盟 API 赚取佣金。
- 内容变现：优质攻略创作者分成、榜单推荐位、商家合作。
- 企业版：旅行社/地接社使用同一平台做团队行程、报价单、客户管理。

## 9. 量化验收指标

| 指标 | 当前大致状态 | P0 后目标 |
|---|---|---|
| 搜索成功率 | 依赖单一 Key，易失败 | ≥99% |
| 单次行程外部 API 调用 | 重复搜索 | 降低 50% |
| 单次行程 token | 全量重生成 | 降低 30%-50% |
| 只改日期 | 全量子 Agent | 只触发 date/weather/route |
| 反思修正 | 不回流 | 明显问题 2 次内修正 |
| 完整生成时长 | 全量 | 首事件 <5s，整体 <90s |
| E2E 评测 | 24 条规则 | 50+ 条 + 人工池 |
| 来源覆盖率 | 部分 | 景点/美食/交通/价格 100% 带来源 |
| 可追踪性 | 进程内指标 | 每 run trace + 成本 + 失败原因 |

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 外部 API 成本过高 | 缓存 + 局部重算 + 免费额度告警 + 用户配额 |
| 抓取内容版权风险 | 只摘要不搬运，保留来源，遵守 robots |
| 价格不实时 | 标注更新时间与“以平台实际为准”，关键价格走官方/开放接口 |
| 大模型输出不稳定 | Validator + 反思重试 + 结构化 schema + 人工复核兜底 |
| 并发量上来后 SQLite 撑不住 | 保留 SQLite 演示模式，生产切 Postgres + Redis |
| 功能膨胀导致项目失控 | 按 P0-P3 分期，每期有验收指标，不做一次性大重构 |


## 13. 落地状态（2026-08-21）

### 已完成

- 搜索链路：SerpAPI/Tavily/Bing 自动降级 + 24h 结果缓存 + 内置语料兜底。
- 反思流程：`_quality_router` 真正按 `quality_ok / retry_count / max_retries` 回流 synthesis 重试。
- 局部调整：主 Agent 输出 `changed_fields`，只改日期不重跑景点/美食，只改交通不重算景点；换城市仍全量重规划。
- Agent 复用：`TravelLLM` 实例缓存、`create_agent` 编译图缓存、共享 `HybridSearcher`。
- 运行追踪：新增 `agent_runs` 表，每次生成保存 run_id、意图、状态、agent_results、token、耗时、错误。
- 管理端：新增 `GET /api/admin/runs`，指标页展示最近 20 次运行记录。
- 真实数据基础：高德 POI/路线已有真实适配，搜索/天气为真实数据，天气城市覆盖扩到 60+ 全国主要城市，公开内容源复用全国坐标表。
